Which database when?

The short answer for almost every prototype and most products: Postgres. The long answer is knowing the six situations where something else wins, and saying so with a reason.

Why Postgres is the default

  • Relational data with joins and transactions (users, orders, check-ins).
  • jsonb columns for flexible data, so you rarely need a separate document DB.
  • pgvector for embeddings and semantic search; full-text search built in.
  • Row-level security for per-user privacy; mature tooling; every AI tool knows it.
  • Managed options: Supabase (plus auth and storage), Neon (serverless, branching), RDS / Cloud SQL.
🎯 Say it like this

"I'll start with Postgres: relational core, jsonb for flexible fields and pgvector for semantic search, so one database covers the MVP. If we outgrow it, the first additions would be Redis for caching and rate limits, and a dedicated vector store only past several million vectors or with heavy filtered search."

Practitioners' consensus: start with pgvector, and treat retrieval quality as a chunking, embedding and reranking problem before it's a database problem. Move when you have real numbers.

Schema design checklist

  • UUID primary keys, created_at/updated_at, foreign keys with sensible on delete.
  • Design from queries: list the top 5 queries, then add an index for each.
  • Normalise core entities; use jsonb for truly variable attributes.
  • Enable RLS on every user-data table; write policies like user_id = auth.uid().
  • Never store secrets or raw card numbers; minimise PII; plan deletion (GDPR/DPDP "right to erasure").
  • Migrations in git (supabase/migrations), never manual production edits.
