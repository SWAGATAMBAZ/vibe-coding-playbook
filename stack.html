Project structure the AI won't get lost in

Frontend essentials for PMs

  • Server vs client components: fetch data and call secrets on the server; use client components only for interactivity ("use client").
  • Every screen has four states: empty, loading, error, success. Ask for all four explicitly.
  • Responsive and accessible: labels, keyboard focus, contrast, 375px width. The web-design-guidelines skill audits this.
  • Optimistic UI for fast-feeling actions (log a habit), with rollback on error.
  • Streaming for long AI responses, so users see progress in under a second.
  • Avoid the "AI look": one accent colour, real hierarchy, no random gradients. The frontend-design skill helps.

Backend essentials

  • API design: REST with nouns (GET /api/checkins, POST /api/checkins), proper status codes, pagination, input validation, consistent error shape.
  • Auth vs authorization: who are you vs what can you touch. Enforce authorization on the server (and RLS in the DB), never only in the UI.
  • Idempotency: a retried "pay" or "create" request must not double-charge or duplicate. Use idempotency keys.
  • Long work goes async: queue it, return 202, notify on completion.
  • Secrets: env vars on the server; .env.example in git; .env never.

The safe LLM call pattern

Six things an interviewer looks for: server-side key, auth, rate limit, minimal data to the model, validated structured output, and a fallback.

Deploy in five minutes

  1. Push to GitHub (/ship opens the PR).
  2. Import the repo in Vercel (or ask Claude to use the Vercel MCP/CLI). Add env vars from .env.example.
  3. Every branch gets a preview URL. Share it in the interview chat or your take-home README.
  4. Python service or worker? Railway / Render / Fly from a Dockerfile.
  5. Static site (like this one)? GitHub Pages.
