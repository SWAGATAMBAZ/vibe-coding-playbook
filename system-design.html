System design for AI PMs: the parts you must name

You won't be asked to shard a database. You will be asked "how would this scale?", "where does the LLM call live?" and "what happens when it fails?". Here are the building blocks, the API gateway in depth, the LLM-specific layer, and a 6-step answer structure.

Reference architecture for an AI product

Read it left to right in an interview: client → CDN → gateway (auth, rate limits) → stateless services → cache / database / queue → LLM gateway and workers, with observability across everything.

The API gateway in depth

An API gateway is the front door for your backend: every client request goes through it before reaching a service. It centralises cross-cutting concerns so each service doesn't reimplement them.

Authentication

Validates API keys / JWTs once, passes user identity downstream.

Rate limiting & quotas

Per user, key or plan tier: "free = 50 AI calls/day".

Routing & versioning

/v1/orders → orders service; canary 5% to v2.

Aggregation (BFF)

One mobile call fans out to 3 services and merges results.

Transformation

Protocol translation (REST ↔ gRPC), request/response shaping.

Caching, logging, CORS, TLS

Edge caching of GETs, access logs, TLS termination, CORS policy.

Gateway vs load balancer vs service mesh

Load balancer spreads traffic across copies of one service. API gateway is the smart front door for clients (auth, limits, routing to many services). Service mesh (Istio, Linkerd) handles service-to-service traffic inside the cluster. For an MVP, your framework's API routes + middleware are your gateway; name the real thing when you talk about scale.

The LLM layer: what's different about AI systems

ConcernPattern
Latency (seconds, not ms)Stream tokens; show progress; precompute (daily suggestions overnight); async jobs for long agent runs.
CostModel routing (small model first, escalate hard cases), prompt caching, response caching for identical inputs, max_tokens caps, per-user budgets.
ReliabilityTimeouts, retries with backoff, fallback model/provider, non-AI fallback response.
CorrectnessStructured output + schema validation; RAG with citations; evals in CI; human review for high stakes.
SafetyInput/output filters, prompt-injection defences, tool permissions, PII redaction.
KnowledgeRAG: chunk → embed → store (pgvector) → retrieve (hybrid + rerank) → generate with citations.
MemoryShort-term (conversation), long-term (user profile/facts in DB), episodic (past interactions, summarised).
ObservabilityTrace every call: prompt version, model, tokens, latency, cost, user feedback (Langfuse, LangSmith).
Quality over timeEval set + online signals (thumbs, edits, accept rate) + regression tests when prompts or models change.

The 6-step system design answer

  1. Requirements: functional (what it does) and non-functional (latency, scale, availability, privacy, cost).
  2. Estimates: users, requests/sec, data size, LLM calls/day × cost per call.
  3. API: 3–5 key endpoints.
  4. Data model: main tables and how they're queried.
  5. High-level design: draw the reference architecture above, adapted.
  6. Deep dives & trade-offs: the bottleneck (usually the LLM: cost/latency), failure modes, privacy, how you'd measure success.

Back-of-envelope cheats

  • 1M daily users × 10 requests ≈ 10M/day ≈ ~115 req/s average; plan for 3–5× at peak.
  • 1 day ≈ 86,400 s (call it 100k). 1M rows × 1 KB = 1 GB.
  • LLM cost/day = calls × (input tokens × input price + output tokens × output price). Then ask: can we cache, batch, precompute or use a smaller model?

Trade-offs to name

Consistency vs availability

Payments need strong consistency; a feed can be eventually consistent.

Sync vs async

Sync is simpler; async survives spikes and slow LLMs.

Build vs buy

Auth, payments, search, LLM gateway: buy for an MVP.

Monolith vs microservices

Start with a modular monolith; split when teams or scaling demand it.

Big model vs small model

Quality vs cost and latency; route by difficulty.

Precompute vs on-demand

Daily suggestions overnight = cheap and instant; chat = on-demand.
