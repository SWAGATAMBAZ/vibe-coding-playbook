Interview · 01

Ace the PM vibe coding interview

What the round looks like, what's actually scored, a 5-step framework with a minute-by-minute plan, the exact words to say, and how to recover when the AI breaks on screen.

The three formats

Live · 45 min

Prototyping case

"Build X for user Y." You scope, prompt, build and demo inside one session. The most common format.

Live · hybrid

Product sense + prototype

A normal product design case where part of the time is building. Meta has run a "product sense with AI" round reported as about 30 minutes of product sense followed by 30 of vibe coding.

Take-home

Homework prototype

Days, not minutes. Graded on the thinking (PRD, trade-offs, metrics) as much as the app. Adobe has used this format.

Reported at Google, Meta, Microsoft, Adobe, Figma and Shopify, mostly for AI PM roles and AI startups. Reports are thin and formats change, so ask your recruiter:

  • Is vibe coding a separate round, or part of product sense?
  • Which tool will I use, and can I use my own laptop and setup?
  • Do I share my screen the whole time? Can I use my own prompt templates?
  • Is the output a working demo, a PRD, or both?

The trap

Polished AI output is a trap. A beautiful UI built in 10 minutes earns little if you can't explain the user, the trade-offs, the metric and the risks. Strong candidates ask what breaks at scale, where the privacy risk is, and which trade-offs engineering would push back on.

1 · Clarify & scope: you think, not the AI

  • Goal: "What's the business goal: acquisition, engagement, retention, revenue, cost?"
  • User: list 2–3 segments, pick one and say why (biggest pain × reachable × aligned with goal).
  • Pain points: list 3, pick the sharpest one.
  • Constraints: platform (web/mobile/voice), data available, privacy, time.
  • Solution: propose 2–3 ideas yourself, pick one, and name the must-haves vs nice-to-haves.

Don't let the LLM write the solution. Use it at most to brainstorm segments, and then pick yourself.

2 · Spec: a one-screen mini-PRD

Ask the AI to draft a PRD from your decisions, using a persona prompt ("You are a senior technical PM with a founder's mindset…"). Then spend 2–3 minutes reviewing it out loud: what's good, what's generic, what's missing. Then have it self-critique, keeping only high-confidence suggestions, and accept the ones you agree with. The spec has:

  • Problem, user, job-to-be-done; 3–5 user stories with acceptance criteria
  • MVP scope (in) and explicitly out of scope
  • Screens / flow, data model, where AI is used and why, fallback when AI is wrong
  • Success metric + guardrail metric

Prompts for every step are on the prompt library page.

3 · Build: thin vertical slice first

  • First prompt: the spec + tech constraints + "build only the core happy path first, with mock data".
  • Get one end-to-end flow working before adding anything. Then add features one prompt at a time.
  • While it generates, narrate: what you expect to see, what you'll check, what you'd do in production.
  • Use mock data or a hard-coded LLM response if API keys aren't available, and say so. A fake that works beats a real one that doesn't.

4 · Verify & debug: out loud

  • Click through as the user. Narrate each step.
  • Edge cases: empty state, long input, invalid input, double submit, slow or failed AI call, mobile width.
  • When something breaks, give a precise fix prompt: what you did, what you expected, what happened, the error text.
  • If a fix loops twice: revert, narrow the request, or simplify the feature. Say why.
  • Incorporate interviewer feedback immediately; it's a test of collaboration.

5 · Metrics, risks, guardrails, next

  • North-star + input metrics tied to the goal and pain from step 1. One guardrail metric (e.g. complaint rate, latency, cost per user).
  • Risks: AI accuracy, privacy, bias, abuse, cost, dependency on one model.
  • AI guardrails: human review for high-stakes actions, confidence thresholds, refusals, transparency to the user, evals before launch.
  • What I'd do next: user test with N people, the experiment you'd run, what you'd build in v2, what you'd cut.

Narration phrases that score

Making a decision

"I'm choosing X over Y because [user/goal reason]; the trade-off is Z, which is fine for an MVP."

Rejecting AI output

"This is plausible but generic. It doesn't account for [constraint]. I'll redirect it to…"

Checking the work

"Before I accept this, let me check the empty case and what happens if the AI call fails."

Production thinking

"For the prototype the key is in an env var; in production this call goes through our backend with rate limiting and logging."

Privacy

"This stores mood notes, which are sensitive. I'd keep them per-user with row-level security and not send names to the model."

Cutting scope

"We have 15 minutes left. I'll drop export and nail the core flow, since that's what proves the hypothesis."

When the AI breaks on screen

  1. Stay calm and narrate. Breakage is an opportunity to show debugging judgement.
  2. Read the error. Say what you think it means.
  3. Precise fix prompt: steps to reproduce, expected, actual, error text, "change only what's needed".
  4. Two strikes rule: if the same fix fails twice, revert to the last working state (git or version history) and re-ask with a smaller scope.
  5. Fake it honestly: swap the broken integration for mock data, say so, and move on to verify and metrics.
  6. Context reset: in Claude Code, /clear and restate the spec; in Lovable/Bolt, start the fix in a fresh message with the full context.

Take-home: what gets you the offer

  • A README with the problem, the user, the decisions you made and why, what you cut, and how to run it.
  • A short PRD/spec in the repo (use the spec-driven flow), with metrics and risks.
  • A deployed link (Vercel/Netlify/Lovable) + a 2-minute Loom walkthrough.
  • Evidence of verification: a few tests, a screenshot of the edge cases handled, a security pass.
  • An "If I had another week" section. This is where your product judgement shows most.

Self-scoring rubric

Score yourself after every mock (0 = missed, 1 = partial, 2 = strong). 16+ out of 20 is ready.

The 10 mistakes that fail candidates

  1. Thinking you're graded on prompts. You're graded on judgement.
  2. Letting the AI choose the user, the problem or the solution.
  3. Dumping the whole problem into one giant prompt.
  4. Accepting clean-looking output without testing it.
  5. Silent building: no narration, or narrating status instead of reasoning.
  6. Skipping self-critique and fact-checking of the PRD.
  7. Repeating a prompt that's going the wrong way instead of resetting.
  8. Building features nobody asked for while the core flow is broken.
  9. No metrics, risks or guardrails at the end.
  10. Hiding AI use, or not being able to explain why the code path is safe.

Follow-up questions to rehearse

How would this scale to 1M users?

Move AI calls behind a backend queue for non-interactive work; cache repeated prompts and embeddings; add rate limits per user; use a cheaper model for simple steps and route hard ones to a bigger model; Postgres with read replicas and indexes; CDN for the frontend; observability on latency, error rate and cost per user.

How do you know the AI part is good enough to launch?

Build an eval set (50–200 real or realistic cases with expected outputs), measure task success and failure modes, set a launch bar with stakeholders, run a shadow or limited beta, track user-facing quality signals (thumbs, edits, rejections) and a human-review sample.

What would engineering push back on?

Calling the LLM from the client, no auth, no rate limiting, schema without indexes, unbounded costs, no tests, vendor lock-in, and anything that stores sensitive data without access controls.

What if the model gives a wrong or harmful answer?

Design for being wrong: show confidence or sources, let the user edit or undo, require confirmation for consequential actions, add a human-review path, filter inputs and outputs, log and review incidents, and have a non-AI fallback.

Why did you choose this tech stack?

Speed to a working demo with production-credible defaults: Next.js + Tailwind + shadcn/ui for UI, Supabase for Postgres + auth + row-level security, Vercel for deploys, server-side LLM calls. Easy for engineers to take over.

How would you measure success?

One north-star tied to user value (e.g. weekly active trackers), 2–3 input metrics (activation, retention D7/D30, AI suggestion acceptance), and guardrails (latency, cost per active user, complaint or opt-out rate). Then name the experiment you'd run.

What did the AI get wrong, and how did you catch it?

Have a real example from your mock: an invented API, a missing auth check, a generic metric, an unhandled empty state. Say how you noticed (running it, reading the diff, an edge-case test) and how you fixed it.
