Spec-driven development: where PMs have the edge

Vibe coding guesses; spec-driven development (SDD) decides first. The spec becomes the source of truth that drives the plan, the tasks, the code and the review. It's the PM's natural home, and the single biggest quality upgrade you can make.

Why specs beat vibes

Pure vibe codingSpec-driven
Starting point"Build me a habit tracker"A spec: user, stories, acceptance criteria, out of scope
Who decidesThe model fills gaps with guessesYou decide; the model asks when unclear
Big featuresDrifts, rewrites, "looks right but doesn't work"Small tasks, each verifiable against the spec
Review"Does it look ok?""Does it meet acceptance criteria #1–5?"
HandoverCode onlySpec + plan + tasks + code + tests: an engineer can take over

Each step writes a file, and you review each file before moving on. Specs describe what and why (no tech stack); the plan describes how.

Writing specs the AI can't misread

  • Acceptance criteria as Given / When / Then. "Given 7+ check-ins, when I open Today, then I see exactly one suggestion with a 'why' under 20 words."
  • Explicit out-of-scope list. The single best defence against feature creep.
  • Name the edge cases: empty, first-time, error, offline, very long input.
  • State non-functional needs: privacy, latency, accessibility, cost ceiling per user.
  • Mark assumptions as [ASSUMPTION] so the clarify step questions them.
  • One spec per feature, not one giant spec for the app.

Don't stack them

Running Spec Kit and Superpowers' planning on the same feature gives Claude two competing processes. Choose one lane per repo and write it into CLAUDE.md.
